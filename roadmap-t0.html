5. Farmer and judge journeys

DECIDED

Primary farmer journey

  1. Farmer opens a blank conversation and sends a vague message.
  2. Sol extracts only explicit facts; the server validates Bangladesh location, numeric ranges, and allowed season values.
  3. The agent asks only for still-missing fields and preserves accepted context.
  4. Sol selects retrieval and weather tools; the server validates and executes them.
  5. Deterministic modules rank crops, compute finance, and build the calendar using retrieved evidence.
  6. Sol explains the result from supplied evidence; UI exposes trace, sources, uncertainties, and assumption labels.
  7. A reload or later turn restores the session from PostgreSQL.
ASSUMED

Four-minute judge demo

  1. 0:00–0:30: State problem, Tier 0 boundary, and real/generated labels.
  2. 0:30–1:20: Start blank; give an incomplete farmer request; show targeted follow-up and memory.
  3. 1:20–2:25: Complete intake; show Sol’s bounded tool sequence and live Open-Meteo values.
  4. 2:25–3:20: Show ranked crops, cited season plan, inspectable finance, and retrieved evidence.
  5. 3:20–4:00: Open raw trace, reload persistence, state limitations, and show local fallback readiness.

The Gazipur button may accelerate recovery during rehearsal, but it must never replace the canonical blank-flow proof.

6. Bounded-hybrid architecture

Farmer
React UI
Express API
Sol bounded planner
Validated tool registry
PostgreSQL + external data
Plan + trace

Sol owns

  • Explicit fact extraction.
  • Next allowed tool selection.
  • Evidence-bound explanation.
  • Stopping when the goal is satisfied.

Server owns

  • Schema/range validation.
  • Tool allow-list and maximum steps.
  • Weather, retrieval, ranking, finance, calendar, persistence.
  • Timeouts, retries, redaction, trace integrity.

Hard guards

  • Bangladesh-only geocoding.
  • No unsupported values or secret-bearing trace.
  • No recursive/delegated tool calls.
  • Maximum eight tool steps and one retry per recoverable external failure.

API contract

POST /api/session/message

{
  "sessionId": "uuid-or-omitted",
  "message": "I have one acre near Gazipur...",
  "clientRequestId": "uuid"
}

The public client never sends a trusted profilePatch; the seeded demo route must be explicitly labeled and removable.

Successful response

{
  "sessionId": "uuid",
  "status": "needs_input | completed",
  "missingFields": [],
  "profile": {},
  "recommendation": {},
  "sources": [],
  "trace": [],
  "warnings": []
}

Errors use a stable code, safe message, retryability, and trace ID; they never expose keys, connection strings, prompts, or stack traces.

OpenAI orchestration contract

  1. Send conversation state, objective, retrieved evidence IDs, and JSON-schema function tools to the Responses API.
  2. Accept only allow-listed tool calls whose arguments pass strict schemas and domain constraints.
  3. Execute deterministic tools; append sanitized raw outputs and provenance to the trace; return tool results to Sol.
  4. Repeat until required evidence exists or the eight-step budget is exhausted.
  5. Validate final response completeness. If invalid, perform one constrained repair; otherwise return a transparent recoverable error.

Retrieval must feed the deterministic crop score, calendar facts, finance labels, and Sol explanation. Merely displaying citations after calculations is not RAG grounding.

Fallback behavior

Weather failure

Return a recoverable error and preserve intake. Never substitute invented weather. Permit a clearly labeled last-known observation only if its timestamp is visible and Koushik approves that behavior.

OpenAI failure

Do not claim autonomous completion. Preserve deterministic tools and previously verified results; show the model failure and retry option. Demo fallback remains explicitly labeled.

Database failure

Do not silently switch to persistent-memory claims. Local memory may support a labeled local demonstration, but target Tier 0 remains blocked until PostgreSQL proof passes.

Evaluation → patch → re-evaluation loop

1. FreezeRubric

Official requirements and judging weights; no moving criteria after seeing results.

2. EvaluateCold run

Score only observed behavior. Keep plan quality, evidence coverage, and execution readiness separate.

3. PatchRoot cause

Fix confirmed critical/high-value defects only; add a failing reproduction first.

4. Re-evaluateFresh proof

Original failure, adversarial paraphrase, regression suite, public readback.

No score is pre-awarded in this roadmap. A score becomes evidence only after a cold run against the exact deployed revision.

11. Definition of Tier 0 done

Tier 0 is done only when all statements below are evidenced against the exact deployed revision. Planned checks, historical handoff claims, local fallbacks, and screenshots without a SHA do not satisfy this definition.

Product and agent gates

  • All eight official Tier 0 capabilities pass end to end.
  • Sol chooses a bounded dependent tool sequence; the server enforces safety and integrity.
  • Missing information is requested precisely and memory survives the required boundary.
  • Weather and retrieved agronomic evidence materially drive advice.
  • Every recommendation and number is traceable to input, source, calculation, or explicit assumption.

Release and evidence gates

  • Focused, regression, failure, browser, secret, and accessibility checks pass.
  • OpenAI, PostgreSQL, Open-Meteo, and DigitalOcean paths are proven live.
  • Public HTTPS judge flow and process-restart persistence pass.
  • README truthfully states tier and real/generated/mock data.
  • Four-minute rehearsal, recovery path, exact local/remote/deployed SHA, and remaining limitations are recorded.
Next-project boundary: after Tier 0 evidence is frozen, create separate checkpoint roadmaps for Tier 1, Tier 2, and other experiments. Reuse the same build → micro-test → repair/advance → cold evaluation loop, but do not let them retroactively weaken Tier 0 evidence.
